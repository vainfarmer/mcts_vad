## Approved Proposal

**Title:** Full-Coverage Comparative VLM Scanning (FCCS): batched all-segment comparative grounding replaces partial-coverage independent segment judging (joint consensus: B's proposal, code-verified, with 3 robustness refinements).

**Mechanism.** Replace the Stage 4 candidate-generation scan architecture with a single full-coverage comparative scan, behind one config switch (default off = byte-identical prior behavior). Pack ALL 6s segments of the video into batched comparative VLM calls over CONTIGUOUS time ranges (batch=8 segments x 2 keyframes = 16 images/call; for >60 segments: batch=16 x 1 keyframe), reusing the already-implemented but currently-dead `scan_segments_comparative` + v57 non-exclusive `segment_scores` schema (verified: zero call sites in the current tree). Each call shows the VLM labeled time ranges of multiple segments from the SAME video and asks it to rate EVERY segment 0-1 using the others as the in-video normal baseline; segments scoring >0.3 become candidates, merged by the existing `_merge_adjacent`, then flow through the UNCHANGED downstream (candidate_top_k=3, v51 half-max boundary detection on the untouched 0.75*CLIP+0.25*MIL curve, v95 TSM + v96 onset/offset confidence modulators, hard NMS, category-aware confidence gates). This changes two mechanistically-inseparable things and only those: (1) COVERAGE: 10-18 of 23-120 segments scanned -> 100%; (2) JUDGMENT MODE: independent per-segment absolute judging (v56-documented to flag 4-6 of any 6 segments SUSPICIOUS at 0.90+) -> relative comparative judging with in-video calibration. They are inseparable because full coverage with independent judging is both latency-prohibitive (~26-50 calls/video) and known-bad (over-flagging at scale makes top_k=3 selection arbitrary), and v56 already isolated the judgment-mode half as mAP-positive — the only untested variable is the coverage extension. When the switch is on, the Stage 3 CLIP-loc region loop and the generic CLIP prescreen are bypassed (verified: `_clip_temporal_localization` is side-effect-free, clip_regions' only consumer is scan direction); the CLIP category curve used by boundary detection is computed independently in `frame_scorer.get_category_scores` and is byte-identical. THREE REFINEMENTS added by consensus after code review: (a) batches must be contiguous time ranges so each segment is calibrated against its temporal neighbors (the correct normal baseline); (b) truncation guard — the comparative prompt must instruct terse output ("description: max 8 words, or null") because max_tokens=512 with 16 JSON entries risks truncated JSON, and `_parse_comparative_response` SILENTLY scores unparseable batches 0.0 (recall loss); on parse failure or missing entries, split the batch in half and retry once, and if still failing, rescan just that batch's segments via the existing independent `scan_segment` path (failure handling only, not a second mechanism); (c) the smoke gate must check BOTH candidate-overlap recovery on known wrong-location videos AND no recall loss on currently-correct smoke videos.

**Rationale.** The roadmap (.qoder/specs/VAD_mAP_50%_优化方案_c990fbf7.md) and v94 logs agree the dominant bottleneck is wrong-location candidates (28.8%), and every alternative signal for fixing it has been eliminated: MIL v6 collapsed (v80-v85b chain, archived; frame-level localization near chance), motion energy is fully wired and cannot help low-motion property crimes, MIL-guided candidates/fusion repeatedly regressed. The VLM is the only signal that works for flat-CLIP videos — but the current architecture never shows it most of the video. Verified v94 full-log traces: directed path scans 10-18 of 23-120 segments (18/120, 12/64, 10/46); fallback path "6/43", "6/32", "6/33 segments passed" with prescreen std 0.001-0.005 (arbitrary selection). If the true event segment is never scanned, the candidate is wrong-location BY CONSTRUCTION; if scanned but flagged at the same 0.90 as 4+ others, candidate_top_k=3 drops it arbitrarily. Full coverage guarantees the true segment is judged; comparative judging ranks it against in-video normal baselines so it survives top-k. Critically, this is NOT a repeat of a buried idea: v56 isolated comparative scanning as mAP-POSITIVE (0.1366->0.1428, +0.006, with then-best AP@0.5/0.7 — confirmed in pipeline.py docstring); v57/v58 regressions were caused by an acceptance-threshold mismatch (0.3->0.5), not the mechanism; v61 reverted the scan mode only inside a bundle whose focus was VLM boundary refinement, so comparative judging was never isolated as harmful. FCCS is the full-coverage generalization the v56 root-cause analysis itself motivates, now applied to BOTH scan paths because B's per-video analysis puts 10/15 zero-IoU videos in the DIRECTED path (no reliable signal-quality gate exists — even cv=0.424 CLIP curves peak at wrong locations for these categories). Mass estimate: recovering 1/3 of ~15 zero-overlap abnormal videos to TP@0.3 adds ~+0.023 mAP; calibration-driven junk-candidate compression lifts precision across all 65 videos. Consensus review confirmed all load-bearing claims against the code and logs (dead code, v56 numbers, coverage traces, v94 aggregates mAP=0.1492/127.56s, side-effect-free Stage 3 skip) and verified the key literature citations via live search.

**Implementation plan.** Back up anomaly_discovery.py, pipeline.py, config.py before editing (working tree is post-v96, uncommitted). 1) config.py / DiscoveryConfig: add `full_coverage_comparative_scan: bool = False` (single switch; False restores exact prior behavior), `comparative_batch_segments: int = 8`, `comparative_keyframes: int = 2`, `comparative_long_segments: int = 60`, `comparative_long_batch: int = 16`. 2) anomaly_discovery.py: (a) extend `scan_segments_comparative()` with optional `category_hint: str = ''` (same CATEGORY_CUES text the directed scan uses) and `keyframes_per_segment: int = 2` (replacing the hardcoded [:2] slice); add "description: max 8 words, or null" to the prompt to bound output tokens; (b) new method `async scan_full_coverage(video_data, context_prompt='', category_hint='')`: take video_data['segments'] in CONTIGUOUS time order, batch per config (N>comparative_long_segments -> batch=comparative_long_batch with 1 keyframe), asyncio.gather one scan_segments_comparative call per batch, collect per-segment confidences via the existing `_parse_comparative_response` (0.3 threshold, unchanged); TRUNCATION GUARD: if a batch's response is unparseable or returns fewer entries than segments, split that batch in half and retry once; if still failing, rescan that batch's segments individually via the existing `scan_segment()` (failure handling only); build candidate dicts in the exact scan_segment-path schema (t_start/t_end/frame_indices/coarse_score/description); return `self._merge_adjacent(candidates)`. 3) pipeline.py detect() Stage 4: if `config.discovery.full_coverage_comparative_scan`: build category_hint from videomae_category + CATEGORY_CUES (same code as `_directed_llm_scan` lines 1276-1279) and call `candidates = await self.discovery.scan_full_coverage(video_data, context_prompt, category_hint)`; else keep the existing `if clip_regions: _directed_llm_scan / else: discover()` branches untouched. When the switch is on, skip the Stage 3 `_clip_temporal_localization` region loop (verified side-effect-free; its only consumer is scan direction) — the CLIP category curve for boundary detection is computed separately in `frame_scorer.get_category_scores` and is unaffected. 4) batch_evaluate.py: add a `--full_coverage_scan` CLI flag threaded through VADConfig.from_args (getattr pattern with default False, matching existing style) so the experiment runs with the switch on and the default remains off. NOTHING else changes: candidate_top_k=3, `_clip_boundary_detection` (v51 half-max + 0.75/0.25 MIL fusion + v95 TSM + v96 onset/offset modulators), Stage 5b VLM boundary estimation for low-CLIP, global_merge, temporal_nms(0.3), PostTighten, ensemble classify, clip_score_curve_correction, MIL sanity check, category conf gates. Validation sequence: (a) unit-test batching/parsing/truncation-guard on synthetic segments incl. a deliberately truncated JSON response; (b) smoke 14 videos with switch on — MUST show candidate-overlap recovery on the 3 known wrong-location smoke videos (Stealing036, Robbery050, Vandalism015) AND no recall loss on currently-correct smoke videos AND no latency blowup; (c) full 65-video eval; keep if mAP >= 0.17 (above the +/-0.03 noise band around 0.149), revert (switch off) if < 0.135.

**Expected gain.** +0.03 to +0.06 mAP (0.18-0.21 range). Composition: (a) wrong-location recovery — ~15/52 abnormal videos currently at IoU<0.05 (B's per-video analysis of v94; consistent with aggregate AP@0.3=0.2046 vs mAP=0.1492 and with verified coverage traces of 10-18/23-120 directed, 6/43-6/32-6/33 fallback); full coverage guarantees their true event segment is scanned and comparative calibration improves its top-3 survival; recovering 1/3 of them to TP@0.3 yields ~+0.023; (b) precision gain from calibration — the v56-documented "flags 4-6 of any 6 segments at 0.90+" over-flagging currently fills candidate_top_k=3 with junk that becomes FPs under greedy matching; relative judging compresses junk scores, lifting AP across all videos (v56 measured +0.006 from comparative judging on top-6 subsets alone; full coverage is the untested amplifier); (c) recall floor protected by the v57 non-exclusive schema (rate every segment; no suppression of multi-event videos) plus the consensus-added truncation guard preventing silent zero-score batches. Floor estimate if only calibration helps and coverage recovery is weak: +0.01-0.02 (0.16-0.17), still above noise if >= 0.17.

**Risks.** (1) Candidate-pool modification is historically the riskiest category (v78 confusion-negatives -0.04, v81 MIL-TAG bundled failure, v92 revoting -0.03). Why this is different: those added a NEW signal source or post-hoc flipped inclusion decisions; FCCS uses the SAME VLM on the SAME segments, changing only coverage and judgment mode — and v56 isolated comparative scanning as mAP-POSITIVE (+0.006, best-ever-at-the-time AP@0.5/0.7) before v58's threshold change (the actual regression cause) and v61's bundled revert buried it. FM1 curve-shape: untouched — relative_scores, MIL fusion, half-max crossing byte-identical. FM2 detection-count: top_k/merge/NMS/gates unchanged bound the downside; calibration should REDUCE junk candidates; residual risk is fewer candidates on videos where junk-flagging accidentally included the true segment — covered by the smoke recall guard. FM3: no self-consistency/temperature diversity — single deterministic call per batch. FM4: no revoting — no already-made decision is flipped; this replaces the initial inclusion mechanism wholesale (v92's lesson concerns post-hoc flips). (2) Attention dilution at 8-16 segments/call vs dedicated 4-image calls may miss subtle anomalies — mitigated by 2 keyframes/segment (1 only for >60-segment videos), category hint, non-exclusive schema, contiguous-batch local calibration, and v56's positive evidence at 6 segments. (3) Batch-boundary calibration drift (a quiet batch's junk scored relatively high) — second-order, since the 0.3 threshold is absolute and top_k=3 bounds candidate count; monitored via smoke. (4) NEW risk found in consensus code review: max_tokens=512 can truncate the 16-entry JSON response and `_parse_comparative_response` silently scores failures 0.0 (recall loss) — mitigated by the terse-description instruction + split-and-retry-once + per-batch independent-scan fallback specified in the plan. (5) VLM stochasticity (+/-0.03) can mask a real gain — mitigated by requiring smoke-set recovery on 3 known wrong-location videos plus no-recall-loss before spending a full eval, and a >=0.17 keep-threshold.

**Latency impact.** Neutral to positive, verified against current code paths. Current directed path issues 10-18 parallel VLM calls/video (4 images each, max_scan = min(max(10, N//5), 18)); fallback path up to 6. FCCS issues ~3.7 calls/video on average (mean ~26 segments / batch 8; max ~120 segments -> 8 calls at batch 16 x 1 keyframe). Fewer, denser calls: total image tokens rise moderately on mid videos (e.g. 50 segments: 100 vs ~40-72 images) but per-request overhead and 429-retry pressure dominate VLM latency, and request count drops 3-4x (also reducing concurrent-request rate-limiting at concurrency=3: up to 54 simultaneous requests -> ~11). Skipping the Stage 3 CLIP-loc loop and generic prescreen saves a small amount of compute. CLIP precompute, VideoMAE, MIL, TSM all unchanged. Expected net: -5 to +10 s/video average vs the ~128s budget (v94 measured 127.56s), longest videos bounded by the 1-keyframe rule. No new per-video VLM calls are added in any path; smoke run must confirm no latency blowup before full eval.

**Literature.** (1) TimeChat (CVPR 2024), VTimeLLM (CVPR 2024), Momentor — video-LLM temporal grounding improves when the model reasons over broader temporal context rather than classifying isolated clips (the basis of the v56 comparative scan, validated positive internally: +0.006 mAP, confirmed in pipeline.py docstring). (2) Holmes-VAU (CVPR 2025 Highlight, arXiv 2412.06171 — verified via live search) — long-term video anomaly understanding with MLLMs; its Anomaly-focused Temporal Sampler exists precisely because WHICH frames/segments the MLLM sees is the bottleneck for long-video anomaly localization; FCCS is the training-free full-coverage limit of that principle (their sampler needs a working anomaly scorer, which we lack for flat-CLIP videos — full coverage needs no scorer). (3) TSPO (AAAI 2026, arXiv 2508.04369 — verified via live search) — Temporal Sampling Policy Optimization: learns sampling policies because partial frame coverage degrades MLLM long-video understanding; supports the coverage mechanism. (4) T3AL (CVPR 2024) — zero-shot TAL via region-level proposal reasoning/suppression rather than per-frame absolute scoring; supports region-relative judgment. (5) LLM-as-a-judge comparative calibration (Zheng et al. 2023, MT-Bench lineage) — relative/paired judgments calibrate better than absolute per-item scores. (6) Learning Event Completeness (ICML 2025, arXiv 2506.13095 — verified via live search) — trained boundary modeling reaches only ~13.6% avg mAP@0.1-0.5 on UCF-Crime with CLIP features, confirming our 14.9% at harder thresholds is near the trained frontier and that boundary-side work has little headroom vs candidate-location work. (7) Internal evidence, all re-verified this review: v56 comparative scan (+0.006, mechanism validated in isolation), v57 non-exclusive schema (recall fix, still in code), v58 (threshold change identified as the regression cause, not the scan mode), v61 (scan-mode revert bundled with unrelated VLM-boundary work — never isolated as harmful), v94 full-run logs (18/120, 12/64, 10/46 directed coverage traces; 6/43, 6/32, 6/33 fallback traces), roadmap Phase 2 (28.8% wrong-location candidates identified as the key bottleneck; its own MIL-TAG/motion alternatives since failed or exhausted), and the archived v80-85b chain (MIL v6 collapse) eliminating the MIL-guided alternative.

## Lessons Learned

- **FM2 (detection-count / candidate-pool risk) refuted for wholesale-mechanism replacement:** the historically riskiest change category (candidate-pool modification: v78 -0.04, v81 bundled failure, v92 -0.03) did NOT regress here, confirming the proposal's core distinction — replacing the initial inclusion mechanism wholesale with the SAME VLM on the SAME segments (changing only coverage + judgment mode) is fundamentally safer than adding new signal sources or post-hoc flipping inclusion decisions. FM1 (curve shape) confirmed untouched as designed; FM3/FM4 confirmed absent by construction.
- **Coverage recovery was the weak half; calibration was the strong half:** the +0.0123 gain landed in the proposal's floor band ("only calibration helps and coverage recovery is weak: +0.01-0.02"), indicating comparative judging's junk-candidate compression delivered precision gains across videos, while the hoped-for recovery of ~1/3 of the ~15 zero-IoU wrong-location videos largely did not materialize. Full coverage alone does not fix wrong-location candidates if the VLM still cannot discriminate the true event segment from its temporal neighbors at batch granularity.
- **Latency cost was real, not neutral:** 141.47s vs 127.56s (+13.9s/video) exceeded the proposal's "-5 to +10 s" estimate — denser image payloads per call (16 images) partially offset the 3-4x request-count reduction, so future batched-VLM designs should budget image-token latency, not just request overhead.
- **Dead-but-intact code + documented positive isolation is a reliable reuse pattern:** resurrecting v56/v57's comparative scan (validated positive in isolation, then buried by an unrelated threshold change and a bundled revert) with the consensus-added truncation guard worked as designed — no silent zero-score batches derailed the run, validating the pre-implementation code-review step that caught the max_tokens=512 truncation risk.
