## 如何解释差异

1. v208 的 0.3636 仅来自 Explosion、Shoplifting 两个视频，不能直接与 14 视频 mAP 比较。但把 v210 限制到这两个视频后 mAP 仍为 0，因此样本数不是全部原因。
2. 历史 v195 的 0.2273 使用相同 14 视频，但检测模型为 qwen-vl-plus；现在该接口返回 404，v210/v211 均使用 qwen3-vl-plus。两次实际 API 请求也没有共享回复，存在输出差异。
3. v210 的 CLIP 使用 force_quick_gelu=True；v211 保留 V2 的原始默认激活配置，和历史日志一样出现 QuickGELU mismatch 提示。CLIP 曲线参与候选筛选、边界和分数，属于实质性差异。不能把激活兼容修正自动视为对现有阈值和 MIL 权重一定更好的配置。
4. 历史是 MPS 环境，本次是 CUDA/common；V2 VideoMAE 参数映射已做当前 Transformers 的兼容修正，并严格加载成功后才运行。没有引入 V3 MCTS 到 V2。
5. v210 的 MCTS 最终接受数是 0，其配对 off/on 结果相同。因此没有证据把 v210 的下降归因于 MCTS 应用后的边界修改；需要在相同 VLM 回复和其他配置下单独隔离 CLIP 激活及其他差异，才能定量归因。

具体例子：Explosion GT=50–70 秒，v210 输出 51.5–53.5 秒（IoU=0.1），v211 输出包含 51.5–62 秒（IoU=0.525）；Shooting GT=266.5–273.5 秒，v210 输出 295.5–303.5 秒，v211 输出 269–272 秒。逐视频完整比较见 per_video_comparison.json。单视频 AP 不应简单平均当作批次 mAP。

## 本次配置与消耗

ViT-L-14/openai，CUDA，视频并发 1，qwen3-vl-plus 检测/分类，V2 默认后处理。只做数据路径适配、UTF-8 读写修复与 VideoMAE state-key 加载兼容修复；检测流程不迁入 V3。命令见 COMMAND.json，代码与原始索引哈希见 manifest.json。

耗时 196.16 秒，平均 14.01 秒/视频；152 次 API 请求，总 182,383 token（输入 169,827，输出 12,556），无失败或未知 usage。v210 的耗时及 token 包含配对分支，不能与 v211 直接当作单分支效率比较。
